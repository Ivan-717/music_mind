## 怎么读

```
recall@k 的上界不是 1 —— 藏 N 首只推 k 首时上界是 min(可检索藏歌数, k) / N。
「占上界」= recall / 上界，才是能跨 k、跨切分比较的那个数。
```

切分有两个，**别混**：

| 切分 | 藏什么 | 该不该信 |
|---|---|---|
| `artist_cold` | 整个艺人的全部曲目一起藏 | **主指标**。这才是真实泛化 |
| `random_item` | 按行随机藏 20% | **乐观值**，报的时候必须标明 |

按行随机会泄露：同专辑/同艺人的近邻留在训练集里，推荐只要说「你听过周杰伦，
再听一首周杰伦」就能命中 —— 命中的是**同专辑近邻**，不是口味泛化。

## 已经定下来的设计结论

前三条是**动手前就写进 phase5 规格**的（预注册，不是事后找补）：

1. `content` 必须显著高于 `random` / `genre_prior`，否则先修 `reco/` 再碰 LLM
2. **如果 `agent_full` 输给 `content` 单独跑，就退回确定性排序，把 LLM 降级成只写解释**
   —— 这条是提前写好的决策规则，不是承诺
3. 逐折报数 + 带上天花板，两个切分都报，`random_item` 必须标明是乐观值

后三条是评估**逼出来的**（记在代码注释和回归测试里，不是文档里）：

4. **探索配额 0.5**（`reco/recall.py`）

   | 配额 | 熟人场景（占上界） | 生人场景（占上界） |
   |---|---|---|
   | 0.0 | 61.6% | 0.5% |
   | 0.3 | 55.6% | 1.4% |
   | **0.5** | **44.0%** | **4.5%** |
   | 0.7 | 25.2% | 5.4% |

   没有配额时排序被 `artist` 分量主导，而**生人场景里要找回的恰恰是陌生歌手** ——
   分数越高的候选越不可能是答案。0.5 是两边都站得住的默认值，
   而且它天然该做成用户可调的旋钮

5. **缺失的分量填 0.5，不做权重重新归一化**。反直觉但实测过：重新归一化会**抬高
   稀疏候选的分数**（只有 artist 一项适用的候选除以 0.25 拿到满分），
   random_item 的占上界从 61.6% 掉到 5.6%
6. **流派分量取「最大份额」不是「份额之和」**。改成求和实测更差：
   random_item 61.6% → 55.2%，artist_cold 0.8% → 1.4%

## 2026-10-08 重跑（M8 后）—— 数字降了，但【不是代码回归】

content 基线在 random_item k=20 上：**0.1865（10-03）→ 0.0187（今天）**。

**判定过程**（三层对照，全部可复现）：

1. 同折对照 `quota=0.0 / 0.5` —— 配额的贡献只有 1.87% ↔ 3.12%，**不是主因**
2. 关掉能量分量复跑 —— 1.25%，**更低** → 3640 首的新能量特征没有拖后腿
3. **git HEAD 旧代码 + 同一数据复跑 —— 逐折逐位一致**
   （0.021 / 0.021 / 0.021 / 0.010 / 0.021，新旧代码输出完全相同）
   → **代码零影响，差异 100% 来自数据环境**

**数据环境变了什么**：库 4617 → 4972 首（M7.2/M8 期间按需入库 + 真实使用长出来的）。

这个评估的口径是「藏起用户已有的 20% 行，看推荐能不能推回来」。
**旧数字高，是因为库里"用户熟悉的艺人"名下几乎只有用户听过的歌**（库里
按需生长，而按需的触发者就是用户的歌单）——推熟人就必然命中藏歌，
这是泄露红利的极端形态。库长大后，薛之谦/李荣浩名下多了大量
**"用户没听过、但很像"**的歌 —— **推它们才是推荐的正确目标** ——
推了它们 = 不命中藏歌 = 数字下降。

**旧的高分是"库里没有干扰项"时代的红利；新数字才是真实库规模下的表现。**

### 这次暴露的真问题（比数字本身重要）

**这个口径在库长大后连 content 和 random 都分不开了**：
artist_cold k=50 上 content 1.2% vs random 3.3% —— random 靠"藏歌占全库
比例"天然命中（推 20 首随机、vdev 的歌占全库约 10%）。预注册规则 1
（content 必须显著高于 random）被触发，**但触发的原因是口径失真，不是排序器变差**。

**待办：评估口径需要重设计** —— 思路是让候选只从「相似艺人池」里选再算召回，
排除 random 靠全库比例的白拿命中；或者换一个"命中用户确实会喜欢的新歌"的
离线代理指标。在此之前，**引用这组数字时必须连口径问题一起说**。

## 2026-10-08（下半场）评估口径 v2 落地 —— 以及它揭示的冷酷事实

设计见 `docs/eval-v2-design.md`。落地：`metrics.py` 加 `lift_over_random` / `novelty_at_k`；
`run_eval.py` 每折现算 random 对照，每行新加 `recall_random / lift / novelty` 三列
（旧列全保留）；新模块 `evals/discrimination.py`（用户区分度）。

### 数字（content / random / genre_prior，artist_cold k=20）

| 系统 | recall | 占上界 | **lift** | novelty |
|---|---|---|---|---|
| content | 0.0030 | 1.2% | **−2%** | 98% |
| random | 0.0080 | 3.2% | 0% | 96% |
| genre_prior | 0.0050 | 2.0% | −2% | 98% |

**content 的 lift 是负的 —— 在这个口径下比瞎猜还差。** 旧口径把这个完全藏住了
（只看 recall 绝对值时，1.2% 的 content 和 3.2% 的 random 都是"接近 0 的小数"，
分不出谁是真信号谁是白拿）。

### 怎么解读这个负数（不是"排序器烂了"）

- random 的 3.2% 靠的是**藏歌占全库比例**（vdev 的歌=库里的热门，随机推也能撞上），
  这是 v2 要剥离的白拿 —— lift 已把它按 0 点扣掉
- content 推的是"像 vdev 的"——在库按需生长之后，这些是**长尾相似**的歌，
  和"vdev 藏起来的那批热门"交集反而少 → lift 为负
- **更深的问题**：这个口径（藏已有的、看能否找回）衡量的是「记忆 + 库结构」，
  **衡量不了推荐的产品价值（推用户会喜欢的新歌）**——而那个**离线没有标签**。
  v2 做到了"不再自欺"（三个数一起诚实地看），但**没能造出一个 content 能赢的任务**。

### 用户区分度（首次运行）

```
A→B (vdev 484 首 → 热歌榜号 61 首)：不可判 —— 留出基数 12 首/折，是噪声
B→A：不可判
```
门槛（`MIN_HIDDEN=30`）按预期拦住了误导性输出。另发现 vdev ↔ lizibin **重合 89%**
（同一个人的两个号）——A/B 选材要先查重合率。**等第二个真实用户出现才能当硬门。**

### 结论（供决策）

1. **content 在现行口径下打不过随机——预注册规则 1 被触发，且这次是真的**
   （不是口径失真，是 lift 扣掉白拿之后依然为负）
2. 下一步的分岔：(a) 造一个 content 能赢的离线任务（无标签是个硬问题）；
   (b) 接受"离线只能守不出错，排序质量靠线上反馈/人工看"；
   (c) 先做可观测性，让真实使用数据把这个问题变成可测的
3. **在解决之前，任何"推荐质量"的说法都要带上这一节**
