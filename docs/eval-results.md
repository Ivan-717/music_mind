## 怎么读

```
recall@k 的上界不是 1 —— 藏 N 首只推 k 首时上界是 min(可检索藏歌数, k) / N。
「占上界」= recall / 上界，才是能跨 k、跨切分比较的那个数。
```

切分有两个，**别混**：

| 切分 | 藏什么 | 该不该信 |
|---|---|---|
| `artist_cold` | 整个艺人的全部曲目一起藏 | **主指标**。这才是真实泛化 |
| `random_item` | 按行随机藏 20% | **乐观值**，报的时候必须标明 |

按行随机会泄露：同专辑/同艺人的近邻留在训练集里，推荐只要说「你听过周杰伦，
再听一首周杰伦」就能命中 —— 命中的是**同专辑近邻**，不是口味泛化。

### k=50 那个 8.0% 不可信

`results/20261004-000049`（deepseek k=50）：

- f4 是「降级丢光」，被显式排除
- f0 / f1 / f3 是 `LLMError: 两次都拿不到合法 JSON`，**而且那一版的表结构还没有
  「有效」列**，所以它们以 0 的形式被算进了平均

现在 `run_eval.py` 已经加了「有效/无效」标记和无效原因，重跑会好，但**历史数字改不了**。

## 已经定下来的设计结论

前三条是**动手前就写进 phase5 规格**的（预注册，不是事后找补）：

1. `content` 必须显著高于 `random` / `genre_prior`，否则先修 `reco/` 再碰 LLM
2. **如果 `agent_full` 输给 `content` 单独跑，就退回确定性排序，把 LLM 降级成只写解释**
   —— 这条是提前写好的决策规则，不是承诺
3. 逐折报数 + 带上天花板，两个切分都报，`random_item` 必须标明是乐观值

后三条是评估**逼出来的**（记在代码注释和回归测试里，不是文档里）：

4. **探索配额 0.5**（`reco/recall.py`）

   | 配额 | 熟人场景（占上界） | 生人场景（占上界） |
   |---|---|---|
   | 0.0 | 61.6% | 0.5% |
   | 0.3 | 55.6% | 1.4% |
   | **0.5** | **44.0%** | **4.5%** |
   | 0.7 | 25.2% | 5.4% |

   没有配额时排序被 `artist` 分量主导，而**生人场景里要找回的恰恰是陌生歌手** ——
   分数越高的候选越不可能是答案。0.5 是两边都站得住的默认值，
   而且它天然该做成用户可调的旋钮

5. **缺失的分量填 0.5，不做权重重新归一化**。反直觉但实测过：重新归一化会**抬高
   稀疏候选的分数**（只有 artist 一项适用的候选除以 0.25 拿到满分），
   random_item 的占上界从 61.6% 掉到 5.6%
6. **流派分量取「最大份额」不是「份额之和」**。改成求和实测更差：
   random_item 61.6% → 55.2%，artist_cold 0.8% → 1.4%

## 怎么重跑

```bash
cd agent-service
# 确定性基线（不花钱，秒级）
.venv/Scripts/python.exe -m musicmind_agent.evals.run_eval --systems content --kind artist_cold
# 带 LLM（花钱，几十分钟）
.venv/Scripts/python.exe -m musicmind_agent.evals.run_eval \
    --systems content,agent_full --providers deepseek --kind artist_cold --k 20
```

结果落在 `evals/results/<时间戳>/results.csv`（**在 .gitignore 里**）。
要长期留档就把汇总贴回这份文档，别只留在 CSV 里 —— 这正是这份文档存在的原因。
